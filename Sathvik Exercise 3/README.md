# SyncTrip CRDT Itinerary Prototype

This Python prototype uses conflict-free replicated data types (CRDTs) to merge itinerary changes made independently on different devices while offline.

## Files

- **crdt.py** defines the merge rules: choose a consistent winner for competing field values and combine sets without duplicates.
- **itinerary.py** manages activities, votes, deletions, saved state, and merging between device copies.
- **demo.py** demonstrates four trip scenarios with Alice, Bob, and Charlie editing offline and then synchronizing their copies.

## Functionality

- Add activities with a title, time, and notes.
- Edit different fields independently so both changes survive synchronization.
- Resolve competing edits to the same field using a logical counter, with the device ID breaking ties.
- Upvote or downvote activities, keeping one current vote per traveler.
- Propose an activity instead of adding it directly. It is marked as proposed until its vote is closed. It joins the itinerary only if its net score is above zero; otherwise it is rejected and old messages cannot bring it back.
- Detect when two travelers change the same field of the same activity offline, and open a vote between the proposed values. The most-voted value wins (the newer edit breaks ties) and syncs to every copy.
- Show field votes under their activity, labeled as a choice between proposed values (for example, times) and kept separate from the activity's upvotes and downvotes.
- Delete activities and prevent older data from bringing them back.
- Save and restore local itinerary data as JSON.
- Merge device copies and display the schedule in time order.

Synchronization is simulated locally. These files do not connect real devices over a network.

## Run the demo

**Trip Scenario 1:** Alice and Bob both edit an itinerary event ("Dinner at 7:00 PM") while offline. Alice changes the time to 7:30 PM. Bob updates the notes to "Vegetarian options available". Concurrently, Charlie adds a new activity "Night Walk", while Alice deletes "Museum Tour". Upon reconnection, the two distinct field edits merge seamlessly without overwriting each other, the new activity persists, and the deleted activity stays deleted.

**Trip Scenario 2:** Alice changes "Lunch" to "Taco Bell" and upvotes it, Bob downvotes it, and Charlie upvotes. The schedule is updated with Taco Bell.

**Trip Scenario 3:** Alice and Bob both edit the time of "Breakfast" (8:00 AM) while offline. Alice changes it to 7:30 and Bob to 8:15. Upon reconnection, the conflict is detected and a vote on Breakfast's time opens. Until the vote closes, the schedule shows the time as `--:--`. Alice votes for 7:30, and Bob and Charlie vote for 8:15, so 8:15 wins +2 to +1 and becomes Breakfast's time on every device.

**Trip Scenario 4:** Alice proposes "Kayaking" and upvotes it. Bob and Charlie both downvote it while offline. Upon reconnection, the votes combine to a net score of -1. When the vote is closed, Kayaking is not added to the itinerary.

To run the demo with all four scenarios, run:

```powershell
python demo.py
```

## Evidence

The `evidence` folder contains results generated by `python demo.py`:

- `demo_output.txt`: Terminal output showing all four scenarios before and after synchronization.
- `scenario_1/`: Each device’s offline and synchronized state for the Dinner, Night Walk, and Museum Tour scenario.
- `scenario_2/`: Each device’s offline and synchronized state for the Taco Bell voting scenario.
- `scenario_3/`: Each device’s state for the Breakfast time vote, at four stages: `offline` (separate edits), `detected` (conflict found, vote open), `voted` (each traveler's own vote, not yet shared), and `synced` (vote closed, 8:15 applied everywhere).
- `scenario_4/`: Each device’s state for the Kayaking proposal at three stages: `offline` (each traveler's own vote), `tallied` (votes combined, proposal still open), and `synced` (vote closed, Kayaking rejected).

The JSON files include activity fields, votes, field-vote (`conflicts`) records, proposals and their `decisions`, logical timestamps, and deletion records. An edited field also stores `base`, the timestamp of the value it replaced, which is how concurrent edits are detected.
